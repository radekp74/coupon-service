## 1. Cel

Dostarczyć `POST /api/v1/coupons`, który tworzy kupon w PostgreSQL, zwraca `201 Created`, zachowuje prezentacyjną postać kodu po trimie i nie pozwala utworzyć dwóch kuponów różniących się wyłącznie wielkością liter.

## 2. Wynik

Po zakończeniu:

- prawidłowy request tworzy dokładnie jeden rekord z `current_uses = 0`;
- `WIOSNA`, `wiosna` i `WiOsNa` współdzielą jeden canonical code;
- baza danych, nie preflight `exists`, jest autorytetem unikalności;
- wyścig wielu requestów daje dokładnie jeden sukces;
- walidacja i konflikt są zwracane jako `application/problem+json` ze stabilnym `code`;
- nie są ujawniane SQL, constrainty ani stack trace.

## 3. Zakres

- value object `CouponCode`;
- value object `CountryCode` oparty na ISO 3166-1 alpha-2;
- niezmienny model `Coupon`;
- `CreateCouponUseCase` i implementacja transakcyjna;
- port `CouponRepository` oraz adapter `JdbcClient`;
- wstrzykiwane `Clock` i generator UUID;
- `POST /api/v1/coupons`;
- request/response DTO;
- mapowanie `INVALID_REQUEST`, `COUPON_CODE_CONFLICT` i `INTERNAL_ERROR`;
- unit tests domeny i use case;
- HTTP integration tests na PostgreSQL Testcontainers;
- deterministyczny test concurrent create z barrier i exact counts;
- machine-readable OpenAPI dla operacji create;
- aktualizacja dokumentacji i bramek repozytorium.

## 4. Poza zakresem

- endpoint wykorzystania kuponu;
- GeoIP i client IP;
- pełna specyfikacja obejmująca redemption i runtime UI/generator OpenAPI;
- metryki biznesowe;

- JaCoCo oraz formatter — pozostają w EMP-008/010.

## 5. Kontrakt wejścia

```json
{
  "code": "WIOSNA",
  "maxUses": 100,
  "countryCode": "PL"
}
```

Reguły:

- `code`: wymagany, trim, 3–64 znaki ASCII `[A-Za-z0-9_-]`;
- canonical code: `toUpperCase(Locale.ROOT)`;
- `maxUses`: 1–1 000 000;
- `countryCode`: wymagany, trim, uppercase, istniejący ISO 3166-1 alpha-2.

## 6. Kontrakt sukcesu

```text
POST /api/v1/coupons
201 Created
Content-Type: application/json
```

```json
{
  "id": "149b508d-3797-466a-859f-5fb0770dcb0d",
  "code": "WIOSNA",
  "createdAt": "2026-08-06T12:30:00Z",
  "maxUses": 100,
  "currentUses": 0,
  "countryCode": "PL"
}
```

`code` zachowuje wartość prezentacyjną po trimie. Lookup i unikalność używają `normalized_code`.

## 7. Kontrakt błędów

| Sytuacja | HTTP | `code` |
|---|---:|---|
| błędny JSON lub pole | 400 | `INVALID_REQUEST` |
| canonical code już istnieje | 409 | `COUPON_CODE_CONFLICT` |
| nieoczekiwany błąd | 500 | `INTERNAL_ERROR` |

Odpowiedź ma typ `application/problem+json`. Tekst `detail` nie jest kontraktem integracyjnym.

## 8. Przepływ aplikacyjny

1. Spring parsuje JSON i wykonuje Bean Validation.
2. `CouponCode` trimuje, waliduje i tworzy canonical value.
3. `CountryCode` normalizuje i sprawdza listę ISO.
4. Use case pobiera UUID z portu i czas z `Clock`.
5. Powstaje `Coupon` z `currentUses = 0`.
6. Adapter wykonuje pojedynczy parametryzowany `INSERT`.
7. PostgreSQL `UNIQUE(normalized_code)` rozstrzyga race condition.
8. SQLSTATE `23505` jest mapowany na `CouponCodeConflictException`.
9. Controller zwraca 201 albo Problem Details.

Nie wolno dodawać `existsByCode` jako mechanizmu spójności.

## 9. Transakcja i współbieżność

- granica transakcji znajduje się na use case;
- create wykonuje jeden insert;
- wiele instancji aplikacji współdzieli constraint PostgreSQL;
- kolejność zwycięstwa oznacza kolejność commit/constraint resolution w bazie;
- test używa `CountDownLatch`, bounded executor i timeoutów;
- test nie używa `Thread.sleep`;
- oczekiwany wynik dla 24 prób tego samego canonical code: `1 × 201`, `23 × 409`, `1` rekord.

## 10. Bezpieczeństwo

- SQL jest parametryzowany;
- odpowiedź błędu nie zawiera constraint name, SQLState ani stack trace;
- request nie jest logowany w całości;
- brak auth jest zgodny z treścią zadania i pozostaje jawnie poza zakresem.
