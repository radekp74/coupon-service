## 6. Kontrakt HTTP

### 6.1. Request

```http
POST /api/v1/coupons/{code}/redemptions
Content-Type: application/json
```

```json
{
  "userId": "customer-123"
}
```

Reguły:

- `code` podlega istniejącemu `CouponCode`: trim, 3–64 ASCII `[A-Za-z0-9_-]`, canonical uppercase `Locale.ROOT`;
- `userId` jest opaque i case-sensitive; nie jest trimowany ani normalizowany;
- `userId` ma 1–128 widocznych znaków ASCII U+0021–U+007E, zgodnie z regexem `^[!-~]{1,128}$` amendmentu EMP-001;
- spacja, tabulator, newline, znaki kontrolne i Unicode są odrzucane jako `400 INVALID_REQUEST`;
- IP ani kraj nie są przyjmowane w body lub publicznym nagłówku;
- nieznane pola JSON są odrzucane zgodnie z istniejącą polityką DTO/OpenAPI;
- identyfikator użytkownika jest deklaracją klienta, a nie uwierzytelnioną tożsamością; ograniczenie jest jawne w README.

### 6.2. Sukces

```http
201 Created
Content-Type: application/json
```

```json
{
  "redemptionId": "c5f51cd5-c77e-4a5b-a6b7-b5085358a4b1",
  "couponCode": "WIOSNA",
  "userId": "customer-123",
  "redeemedAt": "2026-08-06T20:45:00Z",
  "remainingUses": 99
}
```

Reguły:

- `redemptionId` i `redeemedAt` są generowane przez wstrzyknięte porty UUID i `Clock`;
- `couponCode` używa zapisanej formy prezentacyjnej kuponu;
- `userId` jest zwracany dokładnie w formie zaakceptowanej w requestcie;
- `remainingUses = max_uses - current_uses` po zatwierdzonym increment;
- nie jest ustawiany `Location` wskazujący nieistniejący endpoint GET.

## 7. Stabilne błędy i kolejność decyzji

| Kolejność | Sytuacja | HTTP | `code` | Zmiana bazy |
|---:|---|---:|---|---|
| 1 | błędny path/body/JSON | 400 | `INVALID_REQUEST` | brak |
| 2 | canonical coupon code nie istnieje w snapshot lookup | 404 | `COUPON_NOT_FOUND` | brak |
| 3 | Client IP lub GeoIP niewiarygodne | 503 | `GEOLOCATION_UNAVAILABLE` | brak |
| 4 | kraj IP nie odpowiada krajowi snapshotu | 403 | `COUNTRY_NOT_ALLOWED` | brak |
| 5 | rekord zniknął przed lockiem | 404 | `COUPON_NOT_FOUND` | brak |
| 6 | kraj pod lockiem nie odpowiada resolved country | 403 | `COUNTRY_NOT_ALLOWED` | brak |
| 7 | ten user ma już zatwierdzony redemption | 409 | `COUPON_ALREADY_REDEEMED` | brak |
| 8 | limit został osiągnięty | 409 | `COUPON_EXHAUSTED` | brak |
| 9 | nieoczekiwany błąd DB lub invariant | 500 | `INTERNAL_ERROR` | rollback |

Kolejność `country → already redeemed → exhausted` jest celowa:

- request z aktualnie niedozwolonego kraju nie uzyskuje informacji o wcześniejszym użyciu;
- poprawny retry tego samego użytkownika zwraca `COUPON_ALREADY_REDEEMED`, nawet gdy kupon jest już wyczerpany;
- nowy użytkownik przy wyczerpanym limicie otrzymuje `COUPON_EXHAUSTED`.

Tekst `detail` nie jest kontraktem integracyjnym. Kontraktem pozostają HTTP status i stabilny `code`. Odpowiedzi nie ujawniają SQL, constraintów, kraju oczekiwanego, raw IP ani odpowiedzi providera.

## 8. Retry i idempotencja

Brak idempotency key jest świadomym ograniczeniem MVP.

- pierwszy zatwierdzony request zwraca `201`;
- ponowienie z tym samym `coupon + userId` zwraca `409 COUPON_ALREADY_REDEEMED`;
- serwis nie odtwarza pierwotnej odpowiedzi `201` i nie zwraca `200` dla replay;
- po utracie odpowiedzi klient może ustalić, że użycie prawdopodobnie zostało zapisane na podstawie stabilnego kodu `COUPON_ALREADY_REDEEMED`, ale publiczny kontrakt nie udostępnia historii;
- dodanie `Idempotency-Key` wymaga osobnego refinementu i modelu przechowywania odpowiedzi.

## 9. Przepływ poza transakcją

`RedeemCouponService` jest orchestracją bez `@Transactional` na całej metodzie.

1. Walidacja i canonicalizacja `code` oraz `userId`.
2. Snapshot lookup kuponu po `normalized_code` bez locka.
3. Brak kuponu kończy request `404` bez wywołania GeoIP.
4. `ClientIpResolver.resolve(request)`.
5. `GeoLocationResolver.resolve(clientIp)`.
6. Awaria Client IP/GeoIP daje `503` bez transakcji i bez zmian bazy.
7. Wstępne porównanie snapshot country z resolved country.
8. Niezgodny kraj daje `403` bez locka.
9. Orchestrator wywołuje osobny port transakcyjny z canonical code, userId i resolved country.

Nie wykonuje się wstępnego sprawdzania `already redeemed` ani `exhausted` poza transakcją, ponieważ takie wyniki byłyby podatne na race condition i mogłyby naruszać zamrożoną kolejność błędów.

## 10. Granica transakcji

Wymagany jest osobny Spring bean, np. `TransactionalCouponRedemptionService`, wywoływany przez orchestrator przez interfejs/port. Bean:

- nie jest `final`, aby nie łamać proxy CGLIB;
- ma publiczną metodę z `@Transactional`;
- używa propagation `REQUIRED` i domyślnego PostgreSQL `READ COMMITTED`;
- nie wykonuje HTTP, DNS, Client IP ani GeoIP;
- nie korzysta z self-invocation do uruchomienia transakcji;
- nie wymaga `SERIALIZABLE`, JVM locka ani distributed locka;
- nie dodaje automatycznego retry i nie utrzymuje transakcji dłużej niż operacje DB.

## 11. Przepływ pod lockiem

1. `SELECT ... FROM coupons WHERE normalized_code = :code FOR UPDATE`.
2. Brak rekordu → `COUPON_NOT_FOUND`.
3. Ponowne porównanie `coupon.country_code` z resolved country.
4. Niezgodność → `COUNTRY_NOT_ALLOWED`.
5. `SELECT 1 FROM coupon_redemptions WHERE coupon_id=:couponId AND user_id=:userId`.
6. Istniejący rekord → `COUPON_ALREADY_REDEEMED`.
7. `current_uses >= max_uses` → `COUPON_EXHAUSTED`.
8. Wygenerowanie `redemptionId` i `redeemedAt`.
9. `INSERT INTO coupon_redemptions (...)`.
10. `UPDATE coupons SET current_uses = current_uses + 1 WHERE id=:id AND current_uses < max_uses RETURNING current_uses, max_uses`.
11. Brak dokładnie jednego wyniku z update oznacza naruszenie invariant i powoduje rollback jako `INTERNAL_ERROR`.
12. Zwrócenie wyniku i commit.

Constrainty bazy pozostają ostateczną ochroną:

- `UNIQUE(coupon_id,user_id)`;
- `CHECK(current_uses <= max_uses)`;
- foreign key redemption → coupon.

Adapter mapuje na `COUPON_ALREADY_REDEEMED` wyłącznie naruszenie nazwanej reguły `uq_coupon_redemptions_coupon_user`. Naruszenie PK albo innego constraintu pozostaje błędem wewnętrznym.

## 12. „Kto pierwszy, ten lepszy”

Dla jednego kuponu requesty są serializowane przez blokadę w PostgreSQL. „Pierwszy” oznacza transakcję, która jako pierwsza uzyska row lock, a nie najwcześniejszy timestamp rozpoczęcia requestu. PostgreSQL nie daje publicznej gwarancji sprawiedliwej kolejki i API nie obiecuje FIFO.

Dla różnych kuponów nie jest używany wspólny lock aplikacyjny, dlatego transakcje mogą działać równolegle.

## 13. Invariants i rollback

Po każdym commit:

```text
0 <= current_uses <= max_uses
current_uses == count(coupon_redemptions for coupon)
max one redemption for (coupon_id, user_id)
```

Każdy wyjątek po insercie i przed commit musi wycofać zarówno insert, jak i increment. Wymagane testy fault injection:

- błąd po insercie, przed update → brak redemption i niezmieniony counter;
- błąd/zerowy wynik update → rollback insertu;
- unique violation użytkownika → brak incrementu;
- wyjątek mapowany na publiczny błąd nie pozostawia częściowego zapisu.

Testowy fault injection nie może być publiczną flagą, endpointem ani konfiguracją produkcyjną.

## 14. Model danych i migracje

Migracja V1 zawiera wszystkie wymagane elementy spójności redemption:

- `coupon_redemptions`;
- FK do `coupons`;
- unique `(coupon_id,user_id)`;
- country code i timestamp;
- check niepustego user ID.

V1 sprawdza dla `user_id` wyłącznie niepustość po trimie; nie egzekwuje długości 128 ani widocznego ASCII. Amendment EMP-001 zamraża więc nowy kontrakt `^[!-~]{1,128}$`, bez trimowania i normalizacji. Implementacja EMP-004 musi dodać migrację z PostgreSQL `CHECK` constraintem równoważnym temu regexowi oraz sprawdzić zgodność Bean Validation, OpenAPI i testów integracyjnych.

Indeks unique `(coupon_id,user_id)` ma leftmost prefix `coupon_id`, wystarczający dla zapytań sprawdzających użytkownika i liczących użycia w zakresie zadania. Wymagana migracja UserId jest częścią zaakceptowanego scope implementacyjnego, nie nowym amendmentem.

## 15. Porty i typy

Planowany publiczny kontrakt aplikacji:

```java
public interface RedeemCouponUseCase {
    CouponRedemptionResult redeem(RedeemCouponCommand command, HttpServletRequest request);
}
```

`HttpServletRequest` pozostaje wyłącznie na granicy application/web potrzebnej istniejącemu `ClientIpResolver`; nie trafia do domeny, encji ani persistence. Orchestrator najpierw wykonuje snapshot lookup, a dopiero potem wywołuje `ClientIpResolver`, dzięki czemu nieistniejący kupon nie uruchamia GeoIP. Implementacja nie może duplikować parsera EMP-006 ani przekazywać raw IP do transakcyjnego portu — część DB otrzymuje wyłącznie canonical code, `UserId` i `CountryCode`.

Docelowe odpowiedzialności:

- `UserId` — walidacja i forma canonical/trimmed;
- `RedeemCouponCommand` — code i userId;
- `CouponRedemption` — zapisany fakt użycia;
- `CouponRedemptionResult` — dane odpowiedzi;
- `CouponRepository` — snapshot, row lock i increment;
- `CouponRedemptionRepository` — exists/insert;
- `CouponRedemptionTransaction` — krótki atomowy fragment DB;
- `RedeemCouponUseCase` — publiczny kontrakt aplikacji;
- kontroler — HTTP mapping, DTO i przekazanie transportowego requestu do orchestratora; sam nie wykonuje Client IP ani GeoIP.

Ostateczny podział między kontrolerem a orchestrator service może zostać dopasowany do istniejącego stylu, ale publiczny use case nie może przejąć surowego IP ani utrzymywać zewnętrznego calla pod transakcją.

## 22. Failure modes

| Failure | Publiczny wynik | Transakcja / zapis |
|---|---|---|
| invalid input | 400 | nie startuje |
| snapshot not found | 404 | nie startuje |
| Client IP/GeoIP failure | 503 | nie startuje |
| wrong country precheck | 403 | nie startuje |
| not found under lock | 404 | rollback/no write |
| wrong country under lock | 403 | rollback/no write |
| same user | 409 | rollback/no write |
| exhausted | 409 | rollback/no write |
| named unique user violation | 409 | rollback |
| insert failure | 500 | rollback |
| increment/update invariant failure | 500 | rollback insertu |
| DB unavailable/deadlock | 500 `INTERNAL_ERROR` | brak częściowego commit |

W MVP nie ma automatycznego retry DB ani nowego publicznego kodu transient database. Takie rozszerzenie wymaga osobnej decyzji po pomiarach.

## 25. Ryzyka

- **R-001 CRITICAL:** przekroczenie limitu — row lock, conditional update, constraint i exact-count tests.
- **R-002 HIGH:** podwójne użycie usera — explicit check, named unique constraint i same-user race.
- **R-003 MEDIUM:** hot coupon — bardzo krótka transakcja, brak network pod lockiem.
- **R-004 HIGH:** GeoIP pod lockiem — osobny non-transactional orchestrator i proxied transaction bean.
- **R-013 HIGH:** counter drift — jedna transakcja i invariant queries w testach.
- **R-015 MEDIUM:** retry po utracie odpowiedzi — stabilny 409, jawny brak idempotency key.
- **R-016 HIGH:** client-asserted userId może być spoofowany — jawne ograniczenie bez auth.
- **R-017 MEDIUM:** błędna precedence daje niestabilne API — zamrożona kolejność i testy kombinacji stanów.

## 26. Historia review i formalna akceptacja

Pierwszy draft otrzymał rekomendację `REJECT`: kontrakt `userId` był niespójny z EMP-001 i V1, a odpowiedzialność kontrolera/orchestratora wymagała doprecyzowania. Review dopisał formalny amendment EMP-001 oraz potwierdził, że kontroler jedynie przekazuje request, a orchestrator wykonuje snapshot, Client IP i GeoIP poza transakcją.

2026-08-06 Radosław Piątek formalnie zaakceptował:

1. scalenie EMP-005 z EMP-004 jako invariant tej samej transakcji, endpointu i evidence;
2. opaque, case-sensitive `userId` `^[!-~]{1,128}$`, bez trimowania i normalizacji, wraz z DB/Bean Validation/OpenAPI enforcement;
3. retry jako `409 COUPON_ALREADY_REDEEMED`, bez replay i bez przedstawiania go jako pełnej idempotencji;
4. precedence: not found → GeoIP unavailable → wrong country → already redeemed → exhausted;
5. `READ COMMITTED + SELECT FOR UPDATE`, bez HTTP pod lockiem, JVM/Redis locków, retry i custom lock timeout.
