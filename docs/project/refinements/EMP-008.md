## Proponowany model JaCoCo

Przyszła implementacja dodaje oficjalny stabilny **`org.jacoco:jacoco-maven-plugin:0.8.15`**. Nie wolno użyć snapshotu 0.8.16 ani aktualizować wersji bez rzeczywistej potrzeby i formalnego amendmentu.

- agent uruchamia się dla Surefire i Failsafe bez nadpisywania istniejącego `argLine` (`@{argLine}` lub równoważne bezpieczne łączenie);
- dane unit i integration są scalane przed `verify` oraz generują HTML i XML;
- `target/site/jacoco/index.html` i `target/site/jacoco/jacoco.xml` powstają podczas `verify`, lecz nie są commitowane ani eksportowane;
- JaCoCo `check` jest wiązany z `verify`; failure coverage powoduje `BUILD FAILURE` i przez to awarię `make verify`;
- nie ma automatycznego obniżania progów, suppressowania failure ani luźnej komendy jako jedynej bramki;
- opcjonalne `make coverage-report` może jedynie ułatwiać lokalny odczyt; obowiązkowym gate pozostaje Maven `verify`.

Aktualny POM używa standardowego Surefire z Spring Boot parentem oraz `maven-failsafe-plugin:3.5.5`, bez jawnego `forkCount`, `reuseForks` i `argLine`. Implementacja musi zachować tę konfigurację i potwierdzić raportem, że oba typy testów wpływają na coverage oraz że Testcontainers nie zostają zakłócone.

## Metryki, agregacja i exclusions

Zaakceptowane globalne minimum to **LINE >= 80%** oraz **BRANCH >= 70%**. To jest docelowy minimalny gate, nie deklaracja aktualnego wyniku. Pierwszy raport ustala wyłącznie pomiar; wynik poniżej progu wymaga review missed lines/branches i wartościowego testu albo jawnego amendmentu właściciela — nigdy cichego obniżenia, tolerancji lub suppressowania failure.

Zaakceptowany model to kombinacja: globalne LINE/BRANCH oraz jeden łączny gate dla logicznych grup coupon domain, coupon application, coupon persistence i Client IP / GeoIP security-sensitive logic: **LINE >= 75%**, **BRANCH >= 65%**. Pełne nazwy Java package mają zostać odczytane z `src/main/java` podczas implementation checkpointu. Jeżeli JaCoCo nie potrafi wyrazić tej grupy bez objęcia niewłaściwego kodu, implementacja ma się zatrzymać i zgłosić problem — bez obniżenia progu, exclusion albo bezwartościowego testu.

Na początku nie ma żadnych exclusions produkcyjnego kodu — dotyczy to także Spring Boot main, configuration, DTO, exceptions i records/value objects. Bezwzględnie zakazane są exclusions dla domain, application, transakcji redemption, persistence, exception mapping, Client IP, CIDR/trusted proxy, GeoIP, adaptera providera i logiki security/privacy. Ewentualny późniejszy czysto mechaniczny artefakt wymaga dokładnego patternu, uzasadnienia, dowodu braku business/security behavior, wpisu w decision log i ponownego coverage gate; exclusion nie może służyć osiągnięciu progu.

## Manual gap review i polityka testów

Closeout EMP-008 wymaga nie tylko `coverage > threshold`, ale manualnego przeglądu `top missed instructions`, `top missed branches`, exception/validation/transaction/security paths. Nowy test jest dozwolony wyłącznie dla istotnego zachowania, nowej gałęzi, invariantu, security/privacy albo realnej luki z raportu. Testy getterów, pustych konstruktorów i duplikaty istniejącego IT są zabronione.

Zachowany standard EMP-004/009: deterministyczność, brak `Thread.sleep` i publicznej sieci, PostgreSQL Testcontainers dla DB, WireMock dla providerów, exact assertions, privacy-safe diagnostics, cleanup i brak flaky rerun. PIT/mutation testing jest **OUT_OF_SCOPE**: mały serwis ma już kosztowne evidence integration/concurrency, a JaCoCo plus ręczny gap review są proporcjonalne do zadania rekrutacyjnego.
