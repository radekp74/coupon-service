## 1. Znaczenie akceptacji

Akceptacja oznacza zakończony self-review i zamrożenie kontraktu implementacyjnego. Nie oznacza akceptacji firmy rekrutującej. Jej rolą jest zapewnienie, że implementacja zaczyna się bez ukrytych decyzji i że każda późniejsza zmiana jest świadoma.

## 2. Cel

Zaprojektować i zaimplementować REST-owy serwis kuponów, który:

- tworzy kupony;
- traktuje kody bez uwzględniania wielkości liter;
- rejestruje wykorzystanie kuponu;
- gwarantuje, że liczba użyć nie przekroczy limitu przy wielu równoległych requestach;
- pozwala użytkownikowi wykorzystać kupon tylko raz;
- ogranicza użycie do kraju ustalonego z adresu IP;
- przechowuje dane w PostgreSQL;
- jest czytelny, testowalny i możliwy do uruchomienia przez osobę oceniającą.

## 3. Wynik biznesowy

Osoba oceniająca może:

1. utworzyć kupon dla kraju i limitu;
2. wykorzystać go jako określony użytkownik;
3. zobaczyć poprawną odmowę dla nieistniejącego kodu, złego kraju, ponownego użycia i wyczerpania;
4. uruchomić test, który dowodzi poprawności przy współbieżności;
5. odtworzyć środowisko z czystego checkoutu.

## 4. Interpretacja wymagań

### 4.1. Kod kuponu

- po trimie ma 3–64 znaki;
- dozwolone są ASCII letters, digits, `_` i `-`;
- canonical form to uppercase z `Locale.ROOT`;
- `WIOSNA` i `wiosna` są jednym kodem;
- unikalność jest egzekwowana przez bazę, nie przez wcześniejszy `exists()`.

### 4.2. Limit użyć

- `maxUses` jest dodatni i nie większy niż 1 000 000;
- `currentUses` startuje od zera;
- każda zaakceptowana redemption zwiększa licznik dokładnie raz;
- odrzucony request nie zmienia licznika;
- baza nie pozwala na `current_uses > max_uses`.

### 4.3. Kraj

- kupon zawiera ISO 3166-1 alpha-2;
- wejście jest normalizowane do uppercase i walidowane względem listy ISO;
- kraj klienta pochodzi z GeoIP dla wiarygodnie ustalonego client IP;
- mismatch zwraca 403;
- brak wiarygodnego wyniku GeoIP zwraca 503.

### 4.4. Użytkownik

- `userId` jest dowolnym identyfikatorem przekazanym przez klienta;
- po trimie ma 1–128 znaków i nie zawiera znaków kontrolnych;
- unikalność obowiązuje w obrębie kuponu;
- brak osobnego systemu użytkowników i auth jest świadomy.

## 8. Architektura

### 8.1. Styl

Modularny monolit z pakietami funkcjonalnymi. Nie powstaje wielomodułowy Maven build, ponieważ nie ma potrzeby niezależnych artefaktów.

### 8.2. Warstwy

- domain — invariants i value objects;
- application — use cases i transakcje;
- ports — repozytoria, GeoIP, client IP;
- adapters — HTTP, PostgreSQL, zewnętrzny HTTP;
- configuration — wiring i externalized configuration.

### 8.3. Reguły zależności

- domain nie importuje Springa;
- application nie zna JSON ani dostawcy GeoIP;
- adaptery implementują porty;
- controller nie wykonuje SQL;
- repozytorium nie mapuje wyjątków na HTTP;
- error mapping znajduje się na granicy API.

## 9. Model danych

Model jest opisany szczegółowo w [data-model.md](../../architecture/data-model.md).

### 9.1. `coupons`

- UUID primary key;
- presentation code;
- normalized canonical code;
- server-created timestamp;
- positive max uses;
- current uses with bounds;
- ISO country code.

### 9.2. `coupon_redemptions`

- UUID primary key;
- coupon foreign key;
- user ID;
- resolved country;
- redeemed timestamp;
- unique coupon/user pair.

### 9.3. Niezmienność

MVP nie ma update/delete, dlatego `max_uses`, kod i kraj są po utworzeniu niezmienne. Ułatwia to walidację GeoIP poza transakcją, lecz kraj jest ponownie sprawdzany po locku dla obrony kontraktu.

## 10. Kontrakt API

Pełny kontrakt: [api-contract.md](../../api/api-contract.md).

### 10.1. Create

```text
POST /api/v1/coupons
201 Created
```

### 10.2. Redeem

```text
POST /api/v1/coupons/{code}/redemptions
201 Created
```

### 10.3. Błędy

- 400 `INVALID_REQUEST`;
- 403 `COUNTRY_NOT_ALLOWED`;
- 404 `COUPON_NOT_FOUND`;
- 409 `COUPON_CODE_CONFLICT`;
- 409 `COUPON_ALREADY_REDEEMED`;
- 409 `COUPON_EXHAUSTED`;
- 503 `GEOLOCATION_UNAVAILABLE`;
- 500 `INTERNAL_ERROR`.

## 11. Przepływ utworzenia

1. parse i Bean Validation;
2. `CouponCode` canonicalization;
3. `CountryCode` validation;
4. utworzenie UUID i czasu przez injected `Clock`;
5. bezpośredni insert;
6. unique violation mapowane na domain conflict;
7. 201.

Nie wykonujemy `existsByCode` jako mechanizmu spójności. Może być pomocniczym odczytem, ale constraint pozostaje autorytetem.

## 12. Przepływ wykorzystania

### 12.1. Faza poza transakcją

1. walidacja code/userId;
2. odczyt snapshotu kuponu po normalized code;
3. 404, gdy brak;
4. ustalenie client IP;
5. wywołanie GeoIP;
6. 503 przy wyniku niewiarygodnym;
7. wstępna walidacja kraju.

### 12.2. Faza transakcyjna

1. `SELECT ... FOR UPDATE` po normalized code;
2. 404, jeśli rekord zniknął;
3. ponowna walidacja kraju;
4. sprawdzenie istniejącego redemption użytkownika;
5. sprawdzenie limitu;
6. insert redemption;
7. increment counter;
8. odczyt remaining uses;
9. commit.

### 12.3. Rollback

Każdy wyjątek przed commit usuwa skutki insertu i incrementu. Constraint violation user uniqueness jest mapowane na `COUPON_ALREADY_REDEEMED`.

## 13. Współbieżność

### 13.1. Gwarancja

Dla jednego kuponu transakcje są serializowane przez row lock. Dla różnych kuponów mogą działać równolegle.

### 13.2. „Kto pierwszy”

Kolejność oznacza kolejność uzyskania blokady przez transakcję PostgreSQL, nie czas rozpoczęcia requestu na kliencie.

### 13.3. Niedozwolone implementacje

- synchronized lock w JVM;
- `find → if → save` bez locka;
- licznik w pamięci;
- check unikalności wyłącznie w aplikacji;
- call GeoIP pod DB lockiem;
- sleep-based concurrency tests.

## 14. GeoIP i client IP

### 14.1. Provider

Domyślny adapter korzysta z konfigurowalnego HTTPS endpointu ipwho.is i minimalnego zestawu pól.

### 14.2. Timeouty

- connect 500 ms;
- response 1 s;
- brak retry;
- brak circuit breaker w MVP;
- wszystkie awarie techniczne klasyfikowane jako `GEOLOCATION_UNAVAILABLE`.

### 14.3. Lokalny adapter

- profil `local`/`test` może użyć deterministycznego stuba z krajem z konfiguracji;
- wybór `stub` poza tymi profilami powoduje błąd startu;
- Docker Compose lokalnie może użyć `PL`, aby request z loopback był demonstracyjny;
- publiczne API nie przyjmuje nagłówka ani pola nadpisującego kraj.

### 14.4. Testy

- unit test mappera odpowiedzi;
- WireMock: sukces, 429, 500, timeout, malformed JSON, `success=false`, brak country code;
- configuration test blokujący stub w profilu produkcyjnym;
- żadnego publicznego calla w testach.

### 14.5. IP

- remote address jest domyślne;
- forwarded headers tylko za trusted proxy;
- reserved/private IP może dać 503 w realnym adapterze;
- testy używają fake resolvera;
- IP nie jest utrwalany.

## 15. Failure modes

| Sytuacja | Outcome | Zmiana bazy |
|---|---|---|
| niepoprawny request | 400 | brak |
| kod nie istnieje | 404 | brak |
| duplikat create | 409 | brak |
| GeoIP timeout/429/5xx | 503 | brak |
| kraj niezgodny | 403 | brak |
| user już użył | 409 | brak |
| limit osiągnięty | 409 | brak |
| insert redemption fail | 500/409 zależnie od constraintu | rollback |
| increment fail | 500 | rollback insertu |
| DB niedostępna | 500/503 przez global policy | brak częściowego commit |

Globalne mapowanie chwilowej niedostępności bazy może zostać doprecyzowane podczas implementacji bez zmiany domenowych error codes; odpowiedź nie może ujawniać SQL.
