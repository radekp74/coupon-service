## 1. Cel

EMP-010 domyka Wave 6 kontraktu EMP-001 bez rozbudowy funkcji biznesowych. Zadanie ma przenieść istniejący lokalny gate do publicznego CI, utwardzić sposób budowy i eksportu artefaktów oraz dostarczyć minimalną obserwowalność wymaganą już przez EMP-001 i EMP-006.

Refinement został formalnie zaakceptowany 2026-08-07. Stan `READY` oznacza wyłącznie zgodę na osobny checkpoint implementacyjny; CI, delivery i observability evidence pozostają `NOT_MEASURED`, a workflow GitHub Actions, Prometheus, request ID, metryki, digest pins i deterministyczny packager nie są jeszcze zaimplementowane.

## 2. Audyt stanu wejściowego

Stan zweryfikowany przed EMP-010:

- Java 21, Maven Wrapper 3.9.16 z SHA-512 dystrybucji;
- Spring Boot 3.5.16 i PostgreSQL 18.4;
- `make verify` wykonuje governance, Maven/Testcontainers, JaCoCo, DocLint oraz izolowany Docker smoke;
- EMP-008 ma globalnie 96.07% LINE / 86.27% BRANCH i critical aggregate 96.46% / 88.81%;
- 106 unit + 22 integration = 128 testów;
- Docker smoke używa dynamicznego `127.0.0.1` i sprząta wyłącznie własny Compose project;
- `/actuator/health` istnieje, ale `/actuator/prometheus` nie jest wystawiony;
- `micrometer-registry-prometheus` nie występuje w `pom.xml`;
- brak `.github/workflows/ci.yml`;
- Dockerfile używa mutable base-image tags bez jawnego `@sha256`;
- `make export-source` filtruje sekrety i artefakty, ale nazwa zawiera wall-clock timestamp, a ZIP zachowuje zmienne metadane plików, więc nie ma jeszcze byte-for-byte reproducibility;
- request ID i structured JSON logs są zapisane w EMP-001 jako minimalna obserwowalność, lecz nie są jeszcze zaimplementowane.

Dwa historyczne warningi środowiskowe — Flyway o deklarowanym wsparciu PostgreSQL oraz Mockito/ByteBuddy o przyszłym dynamic-agent policy — nie są automatycznie rozszerzane do EMP-010. Mają zostać odnotowane w finalnym review EMP-011, chyba że realnie zepsują CI.

2. utwardzenia Docker/source delivery;
3. deterministycznego artefaktu źródłowego;

## 4. CI — proponowany kontrakt

### 4.1. Workflow

Powstaje jeden workflow `.github/workflows/ci.yml` z jednym głównym jobem `verify`.

Uruchomienia:

- `pull_request`;
- `push` do `main`;
- `workflow_dispatch` do ręcznego odtworzenia gate.

Runner: jawne `ubuntu-24.04`, nie `ubuntu-latest`, aby ograniczyć niejawny drift obrazu CI. Jeden Linux/x64 job wystarcza, ponieważ zadanie nie ma requirementu multiplatformowego, a Testcontainers i Docker Compose są już częścią canonical gate.

### 4.2. Bezpieczeństwo workflow

- `permissions: contents: read` na poziomie workflow/job;
- brak `pull_request_target`;
- brak write permission, deploy key, PAT, registry credential i repo secret;
- wszystkie zewnętrzne `uses:` są przypięte do pełnego 40-znakowego commit SHA; komentarz może wskazywać czytelny upstream release;
- preferowane są wyłącznie oficjalne GitHub actions (`checkout`, `setup-java`, opcjonalnie `upload-artifact`);
- `actions/checkout` używa `persist-credentials: false`;
- żaden krok nie wykonuje kodu z PR z uprzywilejowanym tokenem.

Pełny SHA jest zamrażany podczas implementacji po sprawdzeniu, że pochodzi z oficjalnego repozytorium action. Refinement celowo nie wymyśla SHA bez weryfikacji.

### 4.3. Canonical gate w CI

CI instaluje Temurin Java 21 i uruchamia:

```text
DOCKER=docker make verify
```

To jest ten sam gate co lokalnie; workflow nie duplikuje ręcznie Maven/Testcontainers/JaCoCo/Docker smoke.

Dodatkowo po `make verify`:

- `git diff --exit-code` potwierdza brak modyfikacji tracked source;
- job ma `timeout-minutes: 30`;
- workflow używa `concurrency` z `cancel-in-progress: true`, aby starszy run tej samej gałęzi nie zużywał zasobów;
- cache obejmuje wyłącznie Maven dependency cache przez `setup-java`, nie `target/` ani Docker runtime state.

Nie dodajemy osobnego PostgreSQL service container — integracyjne DB pozostaje własnością Testcontainers.

### 4.4. CI artifacts

Jeżeli `upload-artifact` zostanie użyty, zakres jest ograniczony do diagnostyki:

- `target/surefire-reports/`;
- `target/failsafe-reports/`;
- `target/site/jacoco/`.

Artefakt nie jest release'em i nie może zawierać sekretów. Retencja maksymalnie 7 dni. Brak artefaktu diagnostycznego nie może maskować failure głównego gate.

## 5. Delivery hardening

### 5.1. Docker base images

Po akceptacji oba `FROM eclipse-temurin:21-*-jammy` mają zostać przypięte do immutable digest `@sha256:<64 hex>`. Tag pozostaje jako czytelna etykieta, digest jest autorytetem.

Digest musi zostać zweryfikowany podczas implementacji dla oficjalnego obrazu Eclipse Temurin na Linux/amd64. Nie wolno przepisywać digestu z przypadkowego logu bez sprawdzenia manifestu.

Nie dodajemy prywatnego registry, signing service, Cosign, SBOM pipeline ani deploymentu — są poza zakresem zadania.

### 5.2. Deterministyczny source artifact

`make export-source` ma po implementacji tworzyć artefakt powtarzalny dla tego samego czystego commita:

- wejściem są wyłącznie tracked files z Git, w stabilnie sortowanej kolejności;
- wymagany jest clean working tree;
- root archiwum i nazwa zawierają co najmniej 12 znaków SHA commita, bez wall-clock timestampu wpływającego na bajty;
- ZIP używa stałych metadanych timestamp/permissions oraz stałej metody i poziomu kompresji;
- `.git`, `target`, `build`, `dist`, coverage, IDE cache, logi, nested ZIP, `.env`, klucze i certyfikaty są zabronione;
- packaging nie regeneruje `CHECKSUMS.sha256` i nie mutuje repozytorium;
- stale/missing checksum manifest powoduje failure przed pakowaniem;
- dwa uruchomienia dla tego samego commita w dwóch katalogach wyjściowych muszą mieć identyczny SHA-256.

Preferowana implementacja używa Python 3.9 standard library (`zipfile`) za istniejącym interfejsem `scripts/package_source.sh`, aby wynik nie zależał od BSD/GNU `zip`.

### 5.3. Delivery checker

Powstaje `scripts/check_emp010.py` oraz `make emp010-check`. Checker ma rozdzielać:

- statyczny kontrakt workflow/Docker/Prometheus/request-ID/delivery;
- measured delivery check dla dwóch ZIP-ów lub tryb wykonujący dwukrotny export na czystym checkoutcie.

`make delivery-check` jest dozwolonym osobnym gate post-commit/CI, ponieważ wymaga czystego commita i nie może blokować normalnego `make verify` na roboczym, niecommitowanym kandydacie.

CI po `make verify` uruchamia `make delivery-check`.

## 6. Request ID

Publiczny nagłówek korelacyjny to `X-Request-Id`.

Reguły:

- dokładnie jedna wejściowa wartość może zostać zachowana tylko, gdy pasuje do `^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$`;
- brak, wiele field-lines lub wartość niezgodna z regexem nie odrzuca requestu — serwer generuje nowy UUID;
- odpowiedź zawsze zwraca faktycznie użyty `X-Request-Id`;
- wartość jest umieszczana wyłącznie w MDC pod kluczem `requestId` i czyszczona w `finally` po requestcie;
- request ID nie jest tagiem metryki, kluczem DB ani elementem domeny;
- raw IP, `userId`, coupon code, country klienta i body requestu nie trafiają do MDC;
- test musi dowodzić braku MDC leakage pomiędzy kolejnymi requestami.

Canonical OpenAPI ma opisywać response header `X-Request-Id` dla publicznych odpowiedzi. To nie jest nowy endpoint ani nowa semantyka biznesowa; EMP-001 i `api-contract.md` już przewidują taki correlation header.

## 7. Structured logging

Spring Boot 3.5 ma wbudowane structured logging; EMP-010 nie dodaje zewnętrznego encoder dependency.

W runtime kontenerowym konsola używa formatu `logstash` przez externalized configuration. Wpisy MDC są wtedy polami JSON, więc `requestId` jest dostępny do korelacji.

Wymagania:

- co najmniej runtime Docker/CI używa JSON structured console logs;
- local Maven/test output nie musi być wymuszony do JSON, jeśli pogarsza diagnostykę;
- brak access logów z raw URI, ponieważ ścieżka może zawierać coupon code;
- brak raw IP, `userId`, coupon code, provider body i pełnego provider URL w structured fields;
- nie dodajemy osobnego ELK/Loki/Grafana stacku.

## 8. Prometheus i podstawowe metryki

### 8.1. Registry i endpoint

Po akceptacji `pom.xml` dodaje `io.micrometer:micrometer-registry-prometheus` w wersji zarządzanej przez Spring Boot BOM. Nie przypinamy oddzielnej wersji bez potrzeby.

Actuator exposure:

```text
health,info,prometheus
```

`/actuator/health` nadal ma `show-details: never`. `/actuator/prometheus` nie może ujawniać sekretów ani danych requestu.

### 8.2. Niskokardynalne metryki

Nazwy po stronie Micrometer i zamrożone tagi:

1. Counter `coupon.create`
   - `outcome=success|conflict`

2. Counter `coupon.redemption`
   - `outcome=success|not_found|country_not_allowed|already_redeemed|exhausted|geolocation_unavailable|internal_error`

3. Counter `client.ip.resolution`
   - `source=direct|forwarded|x_forwarded_for`
   - `outcome=success|failure`

4. Counter `geolocation.resolution`
   - `provider=ipwhois|stub`
   - `outcome=success|timeout|rate_limited|provider_error|invalid_response|non_public_ip`

5. Timer `geolocation.provider`
   - `provider=ipwhois|stub`
   - `outcome` z tego samego zamkniętego słownika co `geolocation.resolution`

6. Timer `coupon.redemption.transaction`
   - `outcome=success|not_found|country_not_allowed|already_redeemed|exhausted|database_error`

Prometheus może zmieniać nazwy zgodnie z naming convention (np. counter `_total`, timer `_seconds_*`); kontraktem kodu są nazwy Micrometer oraz zamknięte słowniki tagów.

### 8.3. Cardinality/privacy contract

Bezwzględnie zabronione jako metric tags:

- raw IP;
- `userId`;
- coupon code;
- request ID;
- resolved country;
- pełny URL;
- exception message/class jako swobodny string;
- HTTP query/body.

`outcome`, `source` i `provider` są enum-like i mają zamknięty zbiór wartości.

Nie wymagamy histogram buckets, SLO, alertów ani dashboardu w EMP-010.

## 9. Miejsce instrumentacji

Instrumentacja ma zachować granice architektury:

- domain pozostaje bez Spring/Micrometer;
- nie wprowadzamy AOP tylko dla metryk;
- mały adapter/facade obserwowalności może enkapsulować `MeterRegistry`;
- create i redeem mają dokładnie jeden terminalny business outcome na próbę use case;
- Client IP oraz provider GeoIP instrumentują własne techniczne outcome bez zmiany publicznych wyjątków;
- timer transakcji obejmuje wyłącznie krótką część DB, nie Client IP ani GeoIP.

Jeżeli dodanie metryki wymaga zmiany kolejności błędów, transakcji lub exception contractu, implementacja ma się zatrzymać — metryka nie może zmieniać zachowania.

## 10. Strategia testów EMP-010

### Unit

- request ID: valid incoming reuse, invalid/multiple generate UUID, response header, MDC cleanup;
- metrics facade: exact meter names i exact low-cardinality tags na `SimpleMeterRegistry`;
- provider/client-IP outcome mapping bez publicznej sieci;
- żaden test nie asercjonuje przypadkowego UUID literalnie.

### Integration

- `/actuator/prometheus` zwraca 200 w testowym runtime;
- po kontrolowanych create/redeem scenariuszach scrape zawiera oczekiwane custom meters;
- scrape nie zawiera testowego raw IP, `userId`, coupon code ani request ID jako label value;
- canonical OpenAPI zawiera `X-Request-Id` response header;
- existing 128-test behavior pozostaje semantycznie niezmienione; liczba testów może wzrosnąć.

### Docker smoke

Smoke zachowuje dynamiczny loopback i własny Compose project oraz dodatkowo potwierdza:

- `/actuator/prometheus` jest osiągalny;
- co najmniej standardowy Prometheus payload ma właściwy content type/format;
- odpowiedź HTTP zawiera `X-Request-Id`;
- structured console log runtime jest JSON, bez wymagania zewnętrznego log stacku.

### CI/delivery

- workflow syntax/static checker;
- lokalny `make verify` i GitHub CI uruchamiają ten sam canonical gate;
- dwa source exports tego samego czystego commita mają identyczny SHA-256;
- kontrolowana mutacja wejścia/checksumy musi powodować failure delivery checker;
- source export hygiene pozostaje fail-closed.

## 13. Acceptance criteria

- **AC-01:** `.github/workflows/ci.yml` istnieje i jest syntaktycznie poprawny.
- **AC-02:** CI uruchamia się dla PR, push do `main` i `workflow_dispatch`.
- **AC-03:** runner jest jawnie `ubuntu-24.04`, a Java to Temurin 21.
- **AC-04:** workflow ma wyłącznie `contents: read` i nie używa uprzywilejowanego `pull_request_target`.
- **AC-05:** wszystkie `uses:` są przypięte do pełnego commit SHA zweryfikowanego z oficjalnego repo action.
- **AC-06:** CI nie wymaga sekretów, PAT, deploy key ani registry credentials.
- **AC-07:** CI uruchamia canonical `DOCKER=docker make verify`, bez równoległego alternatywnego gate.
- **AC-08:** CI nie tworzy osobnego PostgreSQL service; integration DB pozostaje Testcontainers.
- **AC-09:** CI ma timeout 30 min, branch concurrency cancellation i po gate potwierdza `git diff --exit-code`.
- **AC-10:** Docker JDK/JRE base images są przypięte do zweryfikowanych immutable `sha256` digestów.
- **AC-11:** `make export-source` nie używa wall-clock danych wpływających na bytes artefaktu.
- **AC-12:** source export używa wyłącznie tracked files, stabilnej kolejności i znormalizowanych ZIP metadata.
- **AC-13:** packaging jest read-only względem repo i nie regeneruje checksumów.
- **AC-14:** stale/missing `CHECKSUMS.sha256` powoduje failure przed exportem.
- **AC-15:** dwa exporty tego samego czystego commita mają identyczny SHA-256.
- **AC-16:** export nadal wyklucza Git, target/build/dist, coverage, IDE cache, logi, ZIP, `.env`, klucze i certyfikaty.
- **AC-17:** `scripts/check_emp010.py`, `make emp010-check` i `make delivery-check` weryfikują rzeczywisty kontrakt, nie tylko dokumentację.
- **AC-18:** `micrometer-registry-prometheus` jest zarządzany przez Spring Boot BOM i `/actuator/prometheus` jest wystawiony obok health/info.
- **AC-19:** istnieją wszystkie sześć zamrożonych meter names z zamkniętymi tag vocabularies.
- **AC-20:** metric labels nie zawierają IP, userId, coupon code, request ID, kraju klienta, pełnego URL ani swobodnego exception text.
- **AC-21:** GeoIP timer nie wykonuje dodatkowego calla ani retry, a transaction timer nie obejmuje GeoIP.
- **AC-22:** `X-Request-Id` zachowuje tylko pojedynczą wartość zgodną z regexem; inaczej generuje UUID bez odrzucenia requestu.
- **AC-23:** faktyczny request ID jest zawsze zwracany w response header, trafia do MDC i jest czyszczony w `finally`.
- **AC-24:** canonical OpenAPI dokumentuje `X-Request-Id` bez zmiany istniejących endpointów/statusów.
- **AC-25:** kontenerowy runtime emituje structured JSON w formacie Logstash przez wbudowane Spring Boot logging.
- **AC-26:** structured logs i metrics zachowują privacy contract EMP-004/006.
- **AC-27:** testy nie korzystają z publicznej sieci i nie wprowadzają H2 ani `Thread.sleep`.
- **AC-28:** Docker smoke potwierdza health, OpenAPI, Swagger, Prometheus, request ID i JSON logging na dynamicznym loopback.
- **AC-29:** EMP-008 thresholds i brak exclusions pozostają bez zmian; pełny `make verify` nadal przechodzi.
- **AC-30:** rzeczywisty GitHub Actions run dla finalnego commita EMP-010 jest zielony oraz `make delivery-check` przechodzi w tym samym runie.
- **AC-31:** brak `CODEX_PROMPT.md`.

## 14. Zaakceptowane decyzje właściciela

Właściciel formalnie zaakceptował 2026-08-07 poniższy zestaw bez rozszerzania scope:

1. **CI:** jeden Ubuntu 24.04 job, Java 21, `DOCKER=docker make verify`, bez matrix i bez osobnego PostgreSQL service — **ACCEPT**.
2. **Action security:** pełne commit SHA, `contents: read`, brak secrets/publish/deploy — **ACCEPT**.
3. **Delivery:** immutable Docker base digests + byte-reproducible tracked-file source ZIP; brak image bit-reproducibility requirement — **ACCEPT**.
4. **Request ID:** strict optional incoming `X-Request-Id`, fallback UUID, response header + MDC cleanup — **ACCEPT**.
5. **Structured logs:** wbudowany Spring Boot `logstash` JSON dla runtime kontenerowego, bez zewnętrznego encoder stacku — **ACCEPT**.
6. **Prometheus:** registry + `/actuator/prometheus` i sześć low-cardinality meter families zgodnych z EMP-001/006 — **ACCEPT**.
7. **Observability scope:** bez Grafany, OTel, alertów, SLO i centralnego log stacku — **ACCEPT**.
8. **Known tool warnings:** Flyway/Mockito warnings pozostają do EMP-011, chyba że staną się realnym blockerem CI — **ACCEPT**.
